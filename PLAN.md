# UMOD Codex GUI — план проєкту (Rust)

> Оновлено 2026-09-18. Попередня редакція описувала Win32-варіант, який так і
> не реалізували, і не згадувала головного блокера — мережі. Ця редакція
> описує проєкт таким, яким він є, і роботу, яка реально лишилась.

## Що це

Окремий GUI-лаунчер для щоденного запуску Codex CLI з профілем `umod`.
Не установник — припускає, що UMOD уже налаштований через UMOD-Installer
(`~/.codex/config.toml`, credential-файл у `~/.umod/`).

Вікно: вибрав модель, натиснув «Запустити» — відкрився Codex.

## Де ми насправді

| Частина | Стан |
|---|---|
| Код GUI (`src/main.rs`, `proxy.rs`, `codex.rs`) | написаний, **жодного разу не проходив `cargo check`** |
| Залежності (vendor) | 959 крейтів, неповні — збірка падає |
| Компіляція | не відбулась жодного разу |
| Тест | не відбувся |

Ключове: «написаний код» не дорівнює «код, що компілюється». У `src/` лежать
три помилки, які компілятор спіймав би за секунду (Етап 1), і один логічний
баг, який вішає вікно на першому ж запуску (Етап 2). Поки `cargo check` не
пройшов, етап «написати код» не закінчений.

## Середовище: чому збірка нетривіальна

**ESET блокує мережу всім Windows-процесам** — `powershell.exe`, `pwsh.exe`,
`git.exe`, `curl.exe`, `cargo.exe`. Відмова за 3–24 мс.

**Мережа є тільки у WSL2** (віртуальний адаптер повз ESET). Git через WSL
працює: `bash -c "git ls-remote https://..."`.

Звідси все інше в цьому плані: будь-яке завантаження робиться **у WSL**, а
Windows-cargo збирає **офлайн** із того, що WSL приніс.

## Технологія

- **Мова:** Rust 1.97.1 (Windows), cargo 1.97.1
- **GUI:** eframe/egui 0.36, `default-features = false`,
  features `["default_fonts", "glow"]`
- **Платформи:** Windows (першочергово), macOS (Етап 8)

### Чому egui, а не Win32 — рішення, яке треба було записати раніше

Попередній план обрав `windows-sys`, бо крейт уже був у кеші, а мережі не
було. Фактично реалізували egui — заради Етапу 8 (macOS): Win32-код довелось
би писати вдруге під Cocoa.

Ціна рішення: близько 1000 крейтів у графі залежностей замість одного, ~100 МБ
vendor і ~15 МБ бінарник замість ~2 МБ. Ціна прийнята свідомо. Якщо macOS з
планів випаде — повернення до `windows-sys` знімає весь Етап 0.

## Як Codex знаходить проксі — це визначає вигляд UI

З `config.toml` установника:

```toml
[model_providers.umod]
base_url = "http://127.0.0.1:8787/v1"
env_key  = "UMOD_PROXY_KEY"
wire_api = "responses"
```

Наслідки, які треба тримати в голові:

1. **Codex не має прапорця `--port`.** Адреса проксі — лише з `config.toml`.
2. **Порт у GUI керує тільки проксі.** Змінив на 8888 — проксі підніметься на
   8888, а Codex і далі піде на 8787 і зависне. Тому порт у GUI або
   редагується разом із `config.toml`, або його в GUI немає (Етап 3).
3. `UMOD_PROXY_KEY` — placeholder, не секрет. Проксі прибирає `Authorization`
   від клієнта і підставляє справжній Entra-токен.
4. Перевіряти проксі треба **HTTP-пробою `/v1/models`**, а не TCP-connect:
   401/403 доводить, що слухає саме проксі, а голий connect зарахує будь-який
   чужий процес на порту. Саме так зроблено в `Umod-Codex.ps1` установника
   («Probe the PORT, not the process»).

## Функції GUI

```
┌─────────────────────────────────────────────────────┐
│  UMOD Codex                                          │
│                                                      │
│  Модель:     [ glm-5.2                    ▼]         │
│  Credential: [C:\Users\...\.umod\a5081.env] [Огляд…] │
│                                                      │
│  Статус проксі: ● працює на 127.0.0.1:8787           │
│                                                      │
│  [ ▶ Запустити Codex ]  [ ⟳ Пуск ]  [ ■ Стоп ]       │
│                                                      │
│  ┌─ Журнал ───────────────────────────────────────┐  │
│  │ [14:30] Проксі запущено                        │  │
│  │ [14:31] Codex запущено з профілем umod         │  │
│  └────────────────────────────────────────────────┘  │
└──────────────────────────────────────────────────────┘
```

1. **Вибір моделі** — glm-5.2 (типово), gpt-5.6-sol/terra/luna, gpt-6-astra,
   deepseek-v4.1-flash
2. **Вибір credential** — поле + «Огляд…», автозаповнення з `~/.umod/`
3. **Статус проксі** — індикатор + текст, оновлюється періодично
4. **Запустити Codex** — піднімає проксі за потреби і запускає Codex
5. **Пуск / Стоп проксі**
6. **Журнал** — події з часовими мітками

Порт у вікні свідомо відсутній: доки не зроблено синхронізацію з
`config.toml` (Етап 3), поле лише вводило б в оману.

## Логіка запуску

```
Користувач → «Запустити Codex»
   ↓
GET http://127.0.0.1:8787/v1/models → проксі відповідає?
   ↓ ні
Запустити python umod-token-proxy (фоновий процес, лог у %TEMP%)
   ↓
Дочекатися відповіді від /v1/models (до 20 с)
   ↓
Запустити codex --profile umod --model <вибрана>   (без --port!)
   ↓ у новому вікні консолі
Codex працює
```

## Етапи

### Етап 0. Зібрати залежності — через WSL, не докачуванням

Скасовано: цикл «`cargo build` → прочитати, якого крейта бракує → докачати
пітоном → 429 → паузи». Це ручний обхід графа на ~1000 вузлів; він не
завершився і не завершиться за прийнятний час.

- [ ] Переконатись, що в WSL є rustup/cargo. Немає — поставити: це швидше,
      ніж доколупувати `fetch_all.py`
- [ ] `wsl bash -lc "cd /mnt/c/Users/Гартунг/Desktop/umod-codex-gui && cargo vendor vendor"`
      — сам обійде `Cargo.lock`, витягне рівно потрібне, покладе
      `.cargo-checksum.json` і надрукує готовий конфіг
- [ ] Прибрати `vendor2.ps1`, `fix-vendor.ps1`, `fix2.ps1`, `fetch_dep.ps1`:
      після `cargo vendor` ручний фікс вкладеності й checksums не потрібен
- [ ] **Прибрати `Cargo.lock` з `.gitignore` і закомітити його.** Для
      бінарника це правильно завжди, а при офлайн-vendor критично: без lock
      граф перерішується і vendor перестає збігатися
- [ ] `cargo build --release --offline` проходить

Альтернатива, якщо vendor не дасться: у WSL виставити `CARGO_HOME` на
Windows-теку і зробити `cargo fetch --target x86_64-pc-windows-msvc`. Тоді
Windows-cargo збирає офлайн із того самого registry, а підміна source у
`.cargo/config.toml` не потрібна взагалі.

Відоме місце ручної правки: у `vendor/egui-winit-0.36.2/Cargo.toml` прибрано
`smithay-clipboard` з feature `clipboard` (Linux-only). Після `cargo vendor`
перевірити, чи це ще потрібно.

### Етап 1. Довести код до `cargo check`

- [ ] `src/main.rs:287` — `ui.min_rect().max.y.checked_sub(1)`: `y` це `f32`,
      `checked_sub` у нього немає. Автоскрол журналу переписати через
      `ScrollArea::stick_to_bottom(true)`
- [ ] `src/main.rs:241` — гілки `if` повертають `&str`, `String`, `&str`.
      Звести до одного типу
- [ ] `src/proxy.rs` — прибрати невикористані `use std::io::{Read, Write}`
      (повернуться на Етапі 3 для HTTP-проби)
- [ ] `cargo check` без помилок — ворота для всього далі

### Етап 2. Протокол каналу — enum, а не пошук підрядка

`src/main.rs:107` визначає стан проксі через `msg.contains("проксі запущено")`,
а надсилається `"Проксі запущено на 127.0.0.1:8787"` — з великої «П». Збігу
немає ніколи: після успішного старту `busy` лишається `true`, `proxy_running`
— `false`, вікно назавжди в стані «запускається…», обидві кнопки мертві.
Гілка «Проксі вже працює» теж не знімає `busy`.

- [ ] `enum ProxyMsg { Started(u16), AlreadyRunning(u16), Failed(String), Log(String) }`
- [ ] `poll_log` перемикає стан за варіантом, а не за текстом
- [ ] Перевірити: після старту індикатор зелений, кнопки живі

### Етап 3. Порт і `config.toml`

- [ ] `src/codex.rs:51` — прибрати `--port {}` з командного рядка Codex:
      такого прапорця немає, запуск падає на розборі аргументів
- [ ] Перевірку проксі перевести з TCP-connect (`src/proxy.rs:29`) на
      HTTP `GET /v1/models` з `Authorization: Bearer probe`; 401/403 = слухає
- [ ] Визначитись із портом: або фіксовані 8787 (просто), або поле в GUI і
      синхронна правка `base_url` у `~/.codex/config.toml` (чесно).
      Проміжного варіанта немає — поле без синхронізації бреше
- [ ] Розглянути виклик `Start-UmodProxy` з `Umod-Codex.ps1` установника
      замість власної копії логіки в Rust: копія вже розійшлася з оригіналом
      (TCP замість HTTP-проби)

### Етап 4. Стоп проксі

`src/main.rs:154` робить `std::mem::forget(state)`, щоб `Drop` не вбив проксі
після завершення потоку, і назавжди губить handle дитини. Тому кнопки «Стоп»
не просто немає — вона при цій архітектурі нездійсненна.

- [ ] Тримати `ProxyState` у `App` (`Arc<Mutex<...>>`), не форгетити
- [ ] Кнопка «Стоп проксі»
- [ ] Вирішити долю проксі при закритті вікна: гасити разом із GUI чи лишати
      жити — і тоді писати PID у файл, щоб наступний запуск його знайшов

## Безпека

- `UMOD_PROXY_KEY` — placeholder, не секрет; проксі підставляє справжній токен
- Credential-файл — єдиний секрет; GUI показує лише шлях, не вміст
- Проксі слухає лише `127.0.0.1`: він додає `Authorization` до всього, що
  пересилає, тож слухач на `0.0.0.0` був би відкритим проксі в платформу
- `.env` і `**/.umod/` — у `.gitignore`
- Бінарник не потребує прав адміністратора

## Критерій готовності

Не «відкрилось вікно», а:

1. `cargo check` і `cargo build --release --offline` проходять з чистого
   клону плюс `cargo vendor`
2. Запуск GUI: індикатор показує реальний стан проксі й міняється після
   «Пуск» і «Стоп»
3. «Запустити Codex» відкриває робочу сесію Codex на моделі зі списку
4. Кривий credential або зайнятий порт дають **повідомлення в журналі**, а не
   мовчазний відкат до значення за замовчуванням
